# 调研与证据边界

## 静态调研边界

只使用浏览器、GitHub 页面/API、官方文档、Release、论文和公开源码页面进行静态调研。**不安装依赖，不运行项目代码，不执行仓库脚本，也不通过 `git clone` 把“可读取”包装成“已验证”。**

当用户只给出名称时，先确认唯一项目、维护者和官方仓库。只有同名项目、产品边界或写作对象确实会改变文章时才提问。

## 来源优先级

1. 官方仓库、README、文档、Release、维护者公告和论文。
2. 可直接阅读的源码、配置、接口定义和测试文件。
3. 有作者、日期和上下文的可靠工程文章或演讲。
4. 社区讨论、Issue、社交平台和媒体报道，仅用于补充观点或热度信号。

搜索摘要、聚合页和二手转述不能单独支撑关键技术结论。相互矛盾时保留冲突，不擅自调和。

## 事实分级

建立内部事实清单，并在正文需要时使用以下标识：

| 标识 | 含义 | 可写范围 |
|---|---|---|
| `[官方声明]` | 官方文字明确宣称 | 写成“官方称/文档显示”，不升级为实测结果 |
| `[源码可见]` | 公开源码或接口中可以直接观察 | 描述结构和静态行为，不声称运行成功 |
| `[社区反馈]` | Issue、讨论或第三方实践 | 说明样本有限，不能代表普遍结论 |
| `[作者分析]` | 根据证据作出的解释或判断 | 明确是分析，不冒充项目方立场 |
| `[未验证]` | 重要但当前无法独立确认 | 降低确定性或从正文删除 |

禁止使用“我实测、我跑通、性能提升了”等运行验证表述。

## 热点判断

综合判断，不把 Stars 总量当作唯一依据：

- 最近一段时间的 Stars、Fork、贡献者或讨论增长；
- 近期 Release、Issue、技术媒体或社区讨论活跃度；
- 技术路线的新颖性及其解决的问题；
- 是否出现多个相互独立的关注来源。

动态数据必须附**查询日期**。无法证明热度时，改写为普通项目介绍，禁用“爆火、刷屏、突然火了”等措辞。

## 停止条件

核心能力、项目身份或关键事实无法由可靠来源确认时，不生成伪完整文章。列出缺失信息并停止。非核心细节无法确认时可以省略，并在 HTML 事实边界注释中说明。
